# Code Quality Rules (Readability / Predictability / Cohesion / Coupling)

이 문서는 "변경하기 쉬운 코드"를 목표로 하며, 아래 4가지 기준을 동일한 우선순위로 관리한다.

- Readability(가독성): 위→아래로 자연스럽게 읽히고, 한 번에 고려할 맥락이 적다
- Predictability(예측 가능성): 이름/반환 타입/부수효과가 일관적이라 동작을 예상할 수 있다
- Cohesion(응집도): 함께 수정되는 것들이 함께 수정되게 구조화한다
- Coupling(결합도): 한 곳 수정의 영향 범위를 작게 유지한다

> Trade-off 주의: 응집도↑(공통화/추상화) 는 결합도↑ 또는 가독성↓를 만들 수 있다.
> 따라서 공통화는 "변경 위험이 큰 곳"에서만, 그 외는 중복을 허용한다.

---

## 1) Readability Rules (가독성)

### R1. 한 덩어리에서 '한 맥락'만 다룬다

- 동시에 실행되지 않는 분기(권한/상태/모드)가 많으면 컴포넌트/함수를 케이스별로 분리한다.
- if/ternary/switch가 UI/로직 전반에 흩어져 있으면 "케이스 컴포넌트"로 쪼개라.

✅ OK: <AdminSubmitButton />, <ViewerSubmitButton />
❌ BAD: 한 컴포넌트에 role 조건이 여기저기 반복

### R2. 구현 상세는 추상화(숨기기)하고 페이지는 '의도'만 남긴다

- 페이지/상위 컴포넌트는 "무엇을 한다"가 먼저 보이게 한다.
- 로그인 체크/리다이렉트/권한 확인 같은 부가 로직은 Wrapper(HOC) or custom hook으로 격리한다.

### R3. 로직 종류가 섞이면 쪼갠다

- 한 함수/훅에 (상태/쿼리파라미터/API/타이머/검증)이 섞이면 책임 단위로 분리한다.
- 분리 기준: 변경 이유가 다르면 분리한다.

### R4. 복잡한 조건/계산/매직 넘버는 이름 붙인다

- 조건이 길어지면 boolean 변수/함수로 추출해 문장처럼 읽히게 한다.
- 매직 넘버는 의미가 드러나는 상수로 치환한다.
  - 예: ANIMATION_DELAY_MS, EMAIL_CODE_TTL_SEC

### R5. 시점 이동(왔다갔다) 최소화

- 핵심 플로우는 위→아래로 읽히게 배치한다.
- helper는 하단으로 내리고, 상단에는 "의도/플로우"를 둔다.
- 중첩 삼항은 단계적으로 풀거나 케이스로 분리한다.
- 비교는 읽는 방향(좌→우)이 자연스럽게 되도록 정렬한다.

## 2) Predictability Rules (예측 가능성)

### P1. 같은 이름은 같은 동작

- 기존 라이브러리/모듈과 동일한 이름으로 래퍼를 만들지 않는다.
  - 예: http 래퍼면 httpClient / apiClient / customHttp 등으로 구분한다.

### P2. 같은 종류의 훅/함수는 반환 타입을 통일한다

- useXxxQuery 계열: 항상 { data, error, isLoading ... } 형태 또는 항상 data만 반환 등 "팀 규칙"을 고정한다.
- 검증 함수: boolean vs 객체 혼용 금지.
  - 권장: { ok: true } | { ok: false; reason: string } (discriminated union)

### P3. 숨은 로직(부수효과) 금지

- 이름/시그니처에 드러나지 않는 logging/analytics/storage write를 내부에서 몰래 하지 않는다.
- 필요하면 옵션/명시적 함수로 분리한다.
  - 예: fetchBalance() + logBalanceFetched()

## 3) Cohesion Rules (응집도)

### C1. 함께 수정되는 파일은 함께 둔다

- 기능(도메인) 단위 디렉토리 선호.
  - 예: /features/auth/\* (components, hooks, api, utils 포함)
- 삭제/변경이 같이 일어나는 코드는 물리적으로 가까이 둔다.

### C2. "같이 바뀌는 값"은 상수/한 곳에서 관리한다

- 매직 넘버/문구/TTL/에러 메시지 등은 SSOT로 모은다.
- UI 애니메이션 시간과 기다리는 delay 값 등은 반드시 연결한다.

### C3. 폼은 필드 단위 응집을 고려한다

- 각 필드는 "입력+검증+메시지"가 가까이 있도록 구성한다.
- 공통 로직은 공유하되, 케이스가 갈라지면 무리한 공통화 대신 분리한다.

---

## 4) Coupling Rules (결합도)

### U1. 영향 범위가 넓어지는 공통화는 금지(기본)

- 공통화(추상화)는 "정말 함께 변하는가"가 확인될 때만 한다.
- 요구사항이 갈라질 가능성이 있으면 중복을 허용한다.

### U2. Props drilling을 줄인다

- 3 depth 이상 props 전달이 반복되면 구조를 재검토한다.
- 대안: context / compound component / store(zustand) / composition

### U3. 책임을 하나씩 관리한다

- 하나의 hook/component가 "상태+API+타이머+검증+UI 메시지"를 모두 책임지면 결합도가 급증한다.
- '경계'를 만든다:
  - API: api 모듈
  - 상태/흐름: hook/VM
  - UI: dumb component

---

## 5) PR Review Checklist

- [ ] 이 변경이 수정/확장하기 쉬운가? (4 기준 중 무엇을 개선/악화시키는지 설명 가능)
- [ ] 가독성: 핵심 플로우가 위→아래로 읽히나? 맥락(분기/조건)이 섞이지 않나?
- [ ] 예측 가능성: 이름/반환 타입/부수효과가 팀 규칙과 일치하나?
- [ ] 응집도: 함께 바뀌는 값/파일이 가까이 있나? SSOT가 있나?
- [ ] 결합도: 공통화가 영향 범위를 키우지 않나? props drilling이 과하지 않나?
- [ ] 트레이드오프: 공통화로 가독성이 떨어졌다면, 그 이유/근거가 PR에 적혔나?

> 협업 우선 원칙(중요):
> 기준이 충돌할 때는 "팀원이 빠르게 이해하고 안전하게 수정할 수 있는가"를 최우선으로 둔다.
> 이를 위해 기본 우선순위는 **R5(시점 이동 최소화)** 이며,
>
> - 읽는 사람이 파일/함수/조건을 왔다갔다 하지 않아도 핵심 흐름을 파악할 수 있도록 한다.
> - 공통화/추상화로 인해 흐름 파악이 어려워진다면(시점 이동 증가), 공통화는 보류하고 중복을 허용한다.
>   단, 보안/결제/권한 등 변경 리스크가 매우 큰 영역은 예외로 응집도(공통화)를 우선할 수 있다(근거를 PR에 명시).
